# v0.3 — the required-context label is circular, and what to do instead

Supersedes the labelling approach in [`v0.2-real-replay.md`](v0.2-real-replay.md), work
package B, and the routing gates in work package D that depend on it. The rest of v0.2 stands.

## What was tried

Five attempts to determine, for a real checkpoint, **which contexts are required to answer
it** — the label `required_context_ids` is defined by. Three of them did not test what they
were meant to and are marked as invalid rather than counted as failures.

| # | instrument | result | what it actually shows |
|---|---|---|---|
| 1 | entity overlap between the reply and each context, argmax | cannot express two contexts; entity filtering removed `dr`, `cn`, `50`, `0.05` from their own contexts | **invalidated** — see below |
| 2 | BM25 of the descriptor against the reply, threshold at half the best | nearly every reply cleared the bar for nearly every context | **invalidated** — see below |
| 3 | distinctive identifiers only (file and artifact names) | 3 of 26 matched the hand labels | **invalidated** — see below |
| 4 | model ablation: hide one context, ask whether the query is still answerable | 0 of 26 exact-set agreement, micro precision 0.236; the model called **all** contexts required on the late checkpoints (8 of 8) | a real failure of that prompt |
| 5 | same ablation with a **presence** question instead of an absence one | answered NO for a context the hand label says is required | **the circularity, isolated** |

### Attempts 1–3 were run on the wrong text

They are not evidence about lexical signals, and it would be wrong to report them as three
failed approaches. All three judged "what the reply says" using an extraction that took the
**first assistant event** after the query — which is normally a tool invocation, or the
one-line preamble the model writes before starting work. Measured on the first real batch:

| | median length | under 120 characters |
|---|---:|---:|
| first assistant event ("the reply") | 72 | 18 of 26 |
| the assistant's actual prose reply | **1 520** | 2 of 26 empty |

The text being reasoned about was a twenty-first the length of the answer, and usually a
`Read {"file_path": …}` line. `answer_after` in `datasets/real_replay.py` now takes the
assistant's `message` events up to the next user turn, excluding tool traffic.

**So the lexical route was never properly tested.** Whether "which contexts does this answer
draw on" is measurable lexically remains open, and the earlier framing of it as settled was
mine to correct.

Attempt 4 fails for a reason worth naming separately: the instruction said *be strict, the
question counts as answerable only if the material contains what is needed*, which puts the
strictness on the wrong side — a strict answerability test makes almost every context look
necessary, and the model complied.

Attempt 5 isolates the real problem.

## The circularity

The ablation shows the model material retrieved from each context — its top events by BM25,
which is what the router's own within-context retrieval would surface. On `q-1216` the model
answered NO for `ctx-q3-env`, the context the hand label says is required. **It was right**:
the retrieved events do not state the answer, so the material genuinely did not contain it.

That is not a prompt bug. It is the shape of the problem:

> To label which context is required, one must know which context contains the answer.
> Determining that means retrieving the answer from within the context — **which is the
> capability the benchmark exists to measure.** The label depends on the thing under test.

The synthetic benchmark is not circular because the generator *constructs* the evidence: it
knows the event ids because it wrote them. Real replay has no such oracle, and every
substitute tried here reduces to "find the answer in the context", i.e. to the task itself.

## What this invalidates

- **Work package B's `required_context_ids` labels** cannot be produced by any instrument
  tried. Of the two attempts that actually ran on the right inputs, one over-called every
  context and the other isolated the reason: the label needs retrieval to determine, and
  retrieval is the thing under test.
- **Work package D's routing gates** — required-context micro recall ≥ 0.95, candidate recall
  ≥ 0.98, cross-context recall ≥ 0.90 — are measured against that label, so they are not
  computable on real replay. The synthetic gates stand, because there the label is exact by
  construction.

The results already reported for the synthetic benchmark are unaffected. So is the finding
that the synthetic router's measured failure is over-selection rather than missing contexts:
that used the synthetic labels.

## What survives, and what to build instead

Real replay can still support the part of the claim that does not need the label. Two gates
survive unchanged, because neither reads `required_context_ids`:

- **Answer quality**, via `answer_requirements` (work package E).
- **Memory tokens**, measured directly.

`answer_requirements` is the label to build on, and it is a different kind of label:

| | `required_context_ids` | `answer_requirements` |
|---|---|---|
| asks | which context is necessary | what a correct answer must contain |
| determined by | a counterfactual over retrieval | reading the assistant's actual reply |
| needs retrieval to label | yes — that is the circularity | no |
| agreement between annotators | unknown, probably low | expected higher: it summarises a text that exists |

So the revised work package B is:

1. For each checkpoint, read the assistant's reply that followed it and write one to three
   requirements stating what a correct answer must contain. No counterfactual, no retrieval.
2. Keep `must_abstain` for the checkpoints where the reply declines.
3. Drop `required_context_ids` from the real-replay schema rather than fill it with something
   unmeasurable. A field nobody can label is worse than no field: it invites a gate.
4. Measure answer quality with the deterministic coverage score plus a blinded judge, and
   report the token cost. That is a claim about routing that real conversations *can* support.

The contingency in v0.2 §"Gate one" then reads differently and more honestly: the offline
routing gates are answered on synthetic data, where the labels are exact; the real-replay
evidence is an answer-quality and cost result, not a recall result.

## What this does not fix

Whether `answer_requirements` labels are reliable is still unmeasured, and it still needs a
second annotator. But the failure mode is now cheap: two annotators disagreeing over a
sentence that summarises an existing reply can be adjudicated by reading it, whereas the
counterfactual could not be adjudicated at all — there was nothing to check against.

## Cost, and what was avoidable

Roughly 240 calls went into this: 117 that produced nothing because the budget was 30x too
small (`--max-tokens 16` forgot that the thinking block shares the budget, a trap this
repository had already diagnosed and written up once), 117 for attempt 4, and 4 for attempt 5.
A further 42 of attempt 4's replies came back empty at a budget of 512, so this model's
thinking exceeds 512 on its own and any call-based work needs at least 1024.

Two avoidable classes, recorded because both recurred:

- **the thinking budget**, already documented here and still walked into;
- **reading the wrong events**, which invalidated three of the six attempts and was only found
  by printing the text being reasoned about and noticing it was a tool call. A cheap "print
  what you are about to judge" check would have caught it on the first attempt.

## Next step

1. **Write `answer_requirements` for the 26 checkpoints** from `answer_after` — the corrected
   extraction, whose output is substantive on 24 of 26. This is offline apart from the model
   that would judge them, and it does not need the counterfactual.
2. **Re-open the lexical question properly**, on the corrected reply text. Attempts 1–3 were
   run on tool calls, so "does the answer draw on this context, judged lexically" has never
   been tested. It is cheap and it is the natural way to cross-check a model judge.
3. **Then the answer-quality gate** (v0.2 work package E) on real conversations: same arms,
   same model, blinded pairwise judging, token cost reported. Routing gates are answered on
   synthetic data; real replay answers the quality and cost question.
