# `ctxlab audit`: five instruments, one judgement

2026-10-02. Offline, deterministic, no judge, no API.

Two of the five diagnostics in this repository exist because a claim was published and then
withdrawn, and the rest exist because a benchmark answered a question it could not answer. A reader
who quotes one number from a report has usually skipped all five, and a report that prints four
tables leaves that choice to the reader. This is the one step:

```bash
ctxlab audit external/pkg_128k_50 --window-size 256 --depth 5 --embedder neural
```

## The five checks and what each prevents

| check | the number whose absence lets a benchmark mislead |
|---|---|
| **arrangement reaches the evidence** | whether the evaluator's own ordering of the stream decided the recency question in advance. A share of 0% or 1% within every query type means the benchmark can only confirm what it was built to confirm |
| **one lookup does not already answer it** | how much of the benchmark a single cheap retrieval answers. When 84% of questions are settled by one BM25 call, a pooled comparison between methods is mostly a statement about the benchmark |
| **enough competitors for a fixed depth to run out** | how many evidence-bearing units compete per retrieved slot. Ten competitors against a depth of five is saturated -- measured, not asserted: the project's own generator reports 0.000 candidate miss in every one of nine configurations |
| **the ordering stage is not the whole gap** | how much of the candidate list's own ceiling the best available ordering leaves unclaimed. When the ceiling is 0.982 and everything reaches 0.51-0.59, no comparison among those orderings is the question |
| **difference is resolvable** | the interval on every difference, so a 0.012 at n = 164 cannot be quoted as a finding |

## Thresholds are declared, not chosen

`SOLVED_SHARE_CEILING = 0.75`, `CORPUS_TO_DEPTH_RATIO = 25`, `RANKING_HEADROOM_CEILING = 0.20`,
`ESTABLISHED_P = 0.05` -- module constants, for the same reason `ORDERING_COMPARISONS` is one: a
report should not be able to pick the rule that flatters it.

## A rule the tool found while being built

The first run on a 50-question package labelled `rrf_score - lexical_rank` **established**, on a
bootstrap interval of `[-0.833, -0.167]`. The exact McNemar p for that row is **0.250**. With three
discordant pairs no bootstrap resample can straddle zero, so the interval excludes it by
construction -- a property of the resampling, not evidence about the difference.

So `is_established` requires **both** tests to agree: the interval excludes zero *and* McNemar
clears 0.05. Everywhere this project says "established" now means that conjunction, including the
`scale-qa` report, which had the weaker rule. This is the sixth instrument-shaped thing this project
has produced, and it was produced by the fifth one being run on something small.

## What it does not cover

- **It audits SCALE-QA packages.** The internal benchmark family reports `recency_reachability` and
  the stage diagnostics through `compare-baselines` and `route-benchmark`, but the difficulty split
  and the ordering attribution have not been ported to it. The gap is stated here rather than
  papered over.
- **It does not measure answer quality.** Nothing in this repository does that in a way the project
  trusts; see the termination statement.
- **`caveat` is not `fail`.** A degenerate arrangement is a failure of the benchmark to be about
  what the report claims; a solved benchmark or a saturated one is usable for other questions. The
  verdict line says which.

*Grade: the checks are exact, deterministic and offline, and are the same measurements the
individual documents report -- this makes them one step and one verdict, and adds no new
measurement. Thresholds are declared in `scale_qa.py` and pinned by tests.*
