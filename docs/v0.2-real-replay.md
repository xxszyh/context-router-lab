# v0.2 — Real Replay and Semantic Routing

## Objective

Turn the Phase 0–1 synthetic result into a reproducible decision about real interleaved
agent conversations:

> On causally replayed, manually labelled Claude Code histories, can the router recover the
> required contexts with at least 95% recall and reduce memory tokens relative to global BM25
> without a material answer-quality loss?

The current evidence licenses this milestone, not automatic memory writing or a context
graph. On held-out synthetic sessions the router reaches evidence recall 1.000 at 642 memory
tokens versus BM25's 750, but required-context recall on the development split is 0.840. A
small private-model answer run supports the direction of the result but is not reproducible.

## Success gates

All metrics are measured on conversations disjoint from training and policy tuning.

| Gate | Target |
|---|---:|
| Candidate required-context micro recall | >= 0.98 |
| Required-context micro recall after selection | >= 0.95 |
| Cross-context recall | >= 0.90 |
| High-confidence routing error | <= 0.02 |
| Future leakage | 0 |
| Median memory-token reduction vs global BM25 | >= 10% |
| Answer quality | non-inferior within the predeclared margin |

Candidate recall and selection recall are separate gates. If a required context never enters
the candidate set, improve retrieval. If it enters and is later dropped, improve reranking,
calibration or the soft-selection policy. No model change is credited without this attribution.

### A. Stage diagnostics and reproducibility

- [ ] Make benchmark reports state which split and routing profile produced them.

Exit: the 0.840 required-context recall has an evidence-backed failure-layer diagnosis.

First diagnostic run on the 60-session synthetic benchmark (780 checkpoints):

| Metric | Result |
|---|---:|
| Candidate required-context recall | 1.000 |
| Selected required-context recall | 1.000 |
| Candidate misses | 0 |
| Selection losses | 0 |
| Selection precision | 0.591 |
| Excess selected contexts | 540 |
| Cases with excess contexts | 280 / 780 |
| Mean candidate / selected contexts | 5.44 / 1.69 |

This benchmark does not currently justify a Transformer as a recall fix: every required
context already reaches the candidate set. Its measured failure is over-selection and
over-confidence. `new_context` and `unanswerable` contribute 300 of the 540 excess contexts;
`cross_context` contributes another 110. The next discriminating test is real replay, where
semantic paraphrase and ambiguous identifiers may create candidate misses that the templated
synthetic data does not.

### B. Real Claude replay dataset

- [x] Import visible Claude Code events locally while omitting hidden thinking and image data.
- [ ] Select 8–15 real contexts from the imported project history.
- [ ] Create 100–200 causally positioned query checkpoints.
- [ ] Label required contexts, equivalent minimal evidence sets and `must_abstain`.
- [ ] Include short coreference, task return, cross-context, same-name identifiers, superseded
  conclusions and incorrect historical assistant claims.
- [ ] Double-annotate at least 20% and record adjudication.
- [ ] Export only a sanitized derivative; never commit the raw conversation database.

Exit: the dataset validates with zero future leakage and has a conversation-level split.

### C. Transformer-assisted semantic retrieval

- [x] Keep `EmbeddingProvider.embed(texts)` as the semantic-model seam.
- [x] Keep deterministic hash and OpenAI-compatible adapters behind that interface.
- [ ] Pin one documented multilingual/code embedding model and record its exact identifier.
- [ ] Compare BM25, transformer bi-encoder, RRF hybrid and the full router on identical splits.
- [ ] Add a cross-encoder only if candidate recall is already high and selection remains the
  dominant loss.
- [ ] Upgrade Relation Lite only if errors concentrate in return, short-coreference or implicit
  cross-context queries.

Transformer models may score candidates. They may not override the causal cutoff, provenance,
tool atomicity, token budget or abstention rules.

Exit: keep a Transformer stage only if it improves a gate metric or reduces selected contexts
at the same recall, with latency and cost reported.

### D. Pass the routing gate

- [ ] Tune the ranker and policy on development conversations only.
- [ ] Freeze thresholds before the final real-replay test.
- [ ] Run ablations: no dense, no entity, no relation, no recency, no calibration and hard route.
- [ ] Report paired conversation-level bootstrap intervals.
- [ ] Publish failure cases, including confident errors and abstentions.

Exit: every routing success gate above passes on the frozen real-replay test.

### E. Reproducible answer-quality gate

- [ ] Use a documented pinned generation model and save `answers.json`.
- [ ] Use an independent judge where possible; preserve every raw judge reply.
- [ ] Keep the deterministic double-refusal gate and report refusal strata separately.
- [ ] Blind a human review of at least 10% of samples.
- [ ] Re-run at 2K, 4K and 8K memory budgets and plot the quality–token frontier.

Exit: answer quality meets the predeclared non-inferiority margin and the run can be reproduced
from saved artefacts.

### F. Conditional product work

Only after D and E pass:

```text
Manual Context State
→ Evidence-linked Memory Writer
→ Dynamic Context Creation
→ Conservative Merge/Split
→ Context Hierarchy/Graph
→ Subagent Scheduling
→ Codex/MCP integration
```

Contexts remain semantic memory units. Subagents remain execution units; no one-to-one mapping
is assumed.

## Non-goals for v0.2

- End-to-end Transformer routing over full histories.
- Automatic context creation, merge/split or graph memory.
- Claiming isolation through MCP while a host also injects full history.
- Optimizing against the final test conversations.
- Treating one LLM judge or one aggregate score as ground truth.
